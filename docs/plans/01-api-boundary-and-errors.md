## 2. Target contract

- Media type `application/problem+json`, fields: `type` (stable URN such as `urn:checkpoint:error:validation`), `title`, `status`, `detail` (safe, public), `code` (stable machine code), `requestId`, optional `errors[]` for validation.
- **Transition shape (backward compatible):** also emit the legacy `error: { message }` key with `message === detail` until Plan 03 has removed all `err.error.error.message` readers. Remove the legacy key in a later release (see decision D1).
- Header `X-Request-Id` on every `/api` response (reuse `context.ts` id; accept a sane inbound `X-Request-Id` only if matching `^[A-Za-z0-9-]{8,64}$`, else generate).
- Status mapping: `AppError` keeps its status and its (Portuguese) message as `detail`; the numeric `code` becomes `status`; a new optional `AppError.errorCode` string supplies `code`, defaulting from status (400 `bad_request`, 401 `unauthenticated`, 403 `forbidden`, 404 `not_found`, 409 `conflict`, 413 `payload_too_large`, 429 `rate_limited`, 502 `upstream_error`, 503 `unavailable`). Any other throwable -> 500, `detail: "Erro interno"`, full error logged with `requestId`. `URIError` -> 400. Postgres errors stay mapped by `asAppError`; unmapped ones are 500.
- Do not rename `AppError.code` (number, used by `server.ts:201` and tests); add a new field instead (compatibility-sensitive).

## 3. Ordered tasks

Each task is one PR-sized change; tasks 1-3 gate the rest.

1. **Contract tests first (characterization).** Add `api/test/errors.test.ts` against `makeServer(service, null)` pinning today's shapes for 400/404/409/413/500 so refactors are visible. Files: new `api/test/errors.test.ts`.
2. **Central error mapper.** New `api/src/errors.ts` exporting `toProblem(e, requestId)` and `problem(status, code, detail)`; extend `AppError` in `api/src/service.ts:41-47` with optional `errorCode`. Replace the catch at `server.ts:198-203`; make `send` accept `application/problem+json`; set `X-Request-Id` at the top of the handler (`server.ts:23-31`); log the real error with `requestId` (single `console.error` call site, to be swapped by Plan 05). Wrap the five `decodeURIComponent` sites with one `safeDecode()` that throws `AppError(…, 400)`. Files: `api/src/errors.ts` (new), `api/src/server.ts`, `api/src/service.ts`, `api/src/wishlist-routes.ts:183`.
3. **Fold the stray error producers into the mapper.** `releases.ts:401-405` returns a throw of `AppError('…', 405)` with an `Allow` header carried by a new optional `AppError.headers`; `wishlist.ts:95` stays (4xx upstream messages are intentional, 502 detail becomes a generic "Serviço externo indisponível" while the original goes to the log); `wishlist.ts:264` replaces raw `e.message` with `e instanceof AppError ? e.message : 'Falha ao importar'` and logs the original. Files: `api/src/releases.ts`, `api/src/wishlist.ts`.
4. **Body reading.** Replace `readJson` (`server.ts:32-47`) with a `Buffer`-based reader: reject early on `Content-Length > LIMIT`, count bytes, 5 s idle timeout, require `application/json` for bodies (415 otherwise; accept absent content-type only on empty optional bodies, see `wishlist-routes.ts:176-179`). Keep the 413 status and the 100 000-byte limit (document it as bytes). Files: `api/src/server.ts` (extract to `api/src/http-body.ts`).
5. **Method handling (405).** After a path matches a known route table but no method matches, respond 405 with `Allow`. Smallest change: keep the current regex dispatch and add a final `if (knownPath) throw AppError(405)` guarded by the matches already computed (`match`, `listMatch`, `scoped`). Do not introduce a router framework (out of scope). Files: `api/src/server.ts`.
6. **Security headers.** Apply to every API response in `send` and the static branch: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin`; add a `headers` block in `vercel.json` for static assets with `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, and a CSP in **Report-Only** first (the Angular build uses inline styles; React/Vite output differs, so enforcement waits for Plan 03). No CORS headers: same-origin only; state this in `docs/deploy.md` and keep `web/proxy.conf.json` for dev. Files: `api/src/server.ts`, `vercel.json`, `docs/deploy.md`.
7. **No-auth guard.** In `authenticatorFromEnv` (`auth.ts:129-137`) return `null` only when `env.ALLOW_INSECURE_DEV_AUTH === '1'` (set by `scripts/dev.mjs` and tests via explicit `makeServer(service, null)`); otherwise fail closed everywhere, including non-Vercel hosts. In `server.ts:207-219` refuse to start with `auth === null` and `HOST` not loopback. Update `.env.example` and README. Files: `api/src/auth.ts`, `api/src/server.ts`, `scripts/dev.mjs` (inspect first; not read in this pass), `.env.example`, `api/test/auth.test.ts`.
8. **Reorder semantics.** Keep the endpoint and `ReorderAccepted` shape; respond **200** unchanged (compatibility), document it as "accepted, not yet persisted", add an `Operation-Id` header equal to the move id (`persistMove` in `service.ts` already creates it), and make `GET /queue/adjustments` (`manualState`) the reconciliation read (it returns `moves` keyed by `client_request_id`, `pg-repository.ts:336`). Persist failures after retries are logged with `requestId`; clients reconcile by refetching `/recommendations`. A durable outbox is deferred (analysis §12.2). Files: `api/src/service.ts`, `api/src/server.ts`, `docs/openapi.json` (document it), `AI/Architecture/back-end/background-reordering.md`.

## 4. Acceptance criteria

- No response body or header on any `/api` path contains text from a non-`AppError` throwable; a test throws `new Error('SECRET')` and `postgres`-style errors from a stub service and asserts a generic 500 body.
- Every `/api` response carries `X-Request-Id`; the same id appears in the 500 body and in the server log line.
- Legacy clients still read `error.message` (task 1 snapshot tests unchanged for AppError cases) until D1 is resolved.
- `DELETE /api/v1/games/x` returns 405 with `Allow`; `GET /api/v1/games/%E0%A4%A` returns 400.
- A 100 001-byte body and an oversized `Content-Length` both return 413 without buffering the whole body.
- Production-like env without `SUPABASE_URL` (with or without `VERCEL`/`NODE_ENV`) returns 503 on every `/api` route except the public ones; starting the server unauthenticated on a non-loopback host exits non-zero.
- Isolation test matrix passes on Postgres for all protected routes; static ownership-filter guard test passes.
- `npm run check` and `npm run architecture:check` pass; `docs/openapi.json` declares the new shapes.

## 6. Risks

- Changing the error body breaks `web/src/{detail,lists,finish-dialog}.ts` readers if the legacy key is dropped early.
- CSP in enforce mode would break the Angular app (inline styles, `index.html` bootstrap); keep Report-Only.
- Task 7 can break `npm start` / `npm run dev` for developers who rely on implicit no-auth; `scripts/dev.mjs` must set the flag.
- Stricter `Content-Type` (task 4) can reject existing callers such as `scripts/record-release.mjs`; check it before enforcing.
- `waitUntil` work can still be lost on instance kill; task 8 documents, it does not eliminate it.

## 7. Dependencies on other plans

- **02 Auth/authz:** owns RBAC and 403 semantics; this plan only adds the stable `forbidden` code and the isolation tests that 02 reuses as its "user A vs B" base. Shared file `api/src/auth.ts`: this plan changes only `authenticatorFromEnv` (task 7); 02 must rebase around it. Resource scoping helper (deny-by-default) is 02's; do not build it here.
- **03 React migration:** its Ky error normalizer must parse `application/problem+json` and fall back to `error.message`; plan 03 states "Backend changes out of scope", so all backend error work lives here and 03 must start after task 2 lands (or mock the new shape). 03 must also stop reading `err.error.error.message` before D1 can drop the legacy key. 03 owns the retry policy; this plan sends no `Retry-After`/idempotency keys yet.
- **04 UI kit:** `ErrorState` consumes the `code`/`requestId` fields defined in section 2.
- **05 Observability:** this plan creates the single log call site and the `requestId` it needs; 05 replaces `console.error` there and owns structured fields, redaction and the collector. The browser collector endpoint must reuse `toProblem` and the body reader from tasks 2 and 4.
- **06 Quality/ops:** shares the OpenAPI contract test and the CI wiring for `isolation.test.ts` (needs a Postgres in CI or a documented manual gate); owns the "single source of truth among Zod/shared/OpenAPI" decision, so task 10 edits the JSON by hand until then.

## 8. Open decisions for the owner

- **D1.** Strict `/api/v1` compatibility (keep legacy `error.message` alongside Problem Details, recommended) versus a controlled break to pure RFC 9457 in `/api/v2`? Default proposed: dual shape now, drop the legacy key after Plan 03 cutover.
- **D2.** Reorder: keep HTTP 200 with documented "accepted" semantics (recommended, zero client change) or move to 202 now (breaking for `web/src/api.ts` expectations)? And is a durable outbox acceptable to defer until failures are observed in logs?
- **D3.** Shared catalog writes (F2a): should `PATCH /games/{id}` restrict `game`-level fields (name, hours, tags) to the creator/an admin, or is community editing intended? This interacts with Plan 02.
- **D4.** Explicit `ALLOW_INSECURE_DEV_AUTH` flag (recommended) versus keeping implicit no-auth outside production.
- **D5.** Is a CSP acceptable to ship as Report-Only until the React build exists, and who watches the reports?
- **D6.** Should the `import-steam` partial-failure `reason` expose any detail to the user, or always a generic message?
- **D7.** Rate limiting (analysis §10.1) is not in this plan: Vercel has no in-process shared state; decide between platform firewall rules and deferring to Plan 06.
