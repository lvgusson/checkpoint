# Plan 02 - Authentication, session and authorization (operational)

Source: `CHECKPOINT_ANALISE_ARQUITETURAL.md` §6, §10.1, §16.3 items 2-3. Verified against the working tree on `main` (71171a6). Status: plan only, no code changed.

## 1. Goal

Keep Supabase Auth and local JWT verification. Close the real authorization gaps found below, make the auth contract testable, and decide (not build) RBAC and the session model. The current product has one role in practice: every authenticated user owns exactly their own data. A role/permission engine is **not** justified until the owner answers D2.

## 3. Ordered tasks

Order is by risk reduction per effort. T1-T4 are independent of any owner decision.

**T1. Characterize current auth (tests first).** Extend `api/test/auth.test.ts` (existing tests at `:39-104`). Add: audience `anon`/missing `sub` rejected; `alg: none` rejected; non-OK `/auth/v1/user` currently yields 401 (document, then fix in T3); JWKS network failure yields 503; unknown `kid` triggers one refetch. Files: `api/test/auth.test.ts`.

**T2. Two-user isolation suite.** New `api/test/isolation.test.ts` (uses the `pg.test.ts` pattern, skipped without `DATABASE_URL`). For users A and B and every route in `server.ts` that takes an id (`/games/:id`, update, reorder, manual adjustments, lists, settings, wishlist import/remove): B receives 404 (never 403, never A's data) and A's rows are byte-identical afterwards. Include F7 as an explicit expectation once D1 is answered; until then record the current behavior as a known-failing test marked `todo`. Files: `api/test/isolation.test.ts`, small helper in `api/test/`.

**T3. Harden the authenticator.** In `api/src/auth.ts`: (a) in `remoteUserFallback`, map 5xx/429 from Supabase to 503 and only 401/403 to 401 (F3); (b) add a short in-memory negative cache keyed by token hash plus a per-IP cap before calling out on HS256 (F9), `// shortcut: per-instance, upgrade to shared store if serverless fan-out matters`; (c) expose `emailVerified` on `AuthUser` from `claims.email_verified` or `user.email_confirmed_at`/`identities`; (d) add a startup check logging a loud warning when `SUPABASE_URL` is set but only the HS256 fallback is reachable (no JWKS keys). Files: `api/src/auth.ts`, `api/test/auth.test.ts`.

**T4. Close the seed-claim hole (F8).** In `api/src/app-user.ts:236`, require `emailVerified === true` for the seed binding and pass it via `RequestContext` (`api/src/context.ts`, add `emailVerified?: boolean`; set in `server.ts:70`). Unverified users still get an empty `app_user` (`:245`). Test: unverified email equal to the seed email does not claim the seed. Operational step: owner verifies hosted `enable_confirmations` (D4). Files: `context.ts`, `app-user.ts`, `server.ts` (one line, coordinate with Plan 01), `api/test/auth.test.ts` or `isolation.test.ts`.

**T5. Fail-closed boot guard (F4).** In `server.ts:208-216`, refuse to listen when auth is null and `HOST` is not loopback unless `ALLOW_INSECURE_NO_AUTH=true`. Delivered by Plan 01 (it owns `server.ts`); this plan only contributes the acceptance test. Files: `api/src/server.ts`, `api/test/auth.test.ts`.

**T6. Resolve F7 (depends on D1).** Option A (private catalog): add `game.owner_user_id` or copy-on-write so `UPDATE game` is restricted to rows the caller owns; new migration in **both** trees (F14). Option B (shared catalog by design): split user-editable fields (`review_notes`, hours overrides) into `library_entry`/overrides, leaving `game` writable only by a privileged path. Option C: accept and document. Files: new migration under `supabase/migrations/` (and `db/migrations/` if still canonical), `api/src/pg-repository.ts:181-239`, `api/src/wishlist-repository.ts:140-160`, tests from T2.

**T7. Introduce a minimal authorization seam (no RBAC engine).** Add `api/src/authz.ts` exporting `type Permission = 'library:read' | 'library:write' | ...` and `authorize(user, permission, resource?)`. Initial policy: a single `member` role holding all permissions, keyed by `app_user.id`; deny by default for unknown permissions; resource scope is always "owner = current app_user". Wire it where `auth.authenticate` returns in `server.ts:69` and in `createAppUserResolver`. Keep Supabase `role` (`authenticated`) separate from product roles (analysis §6.4). Do **not** add CASL, runtime-editable roles or organizations (D2). Files: `api/src/authz.ts`, `api/src/server.ts`, `api/src/context.ts` (add `roles?: string[]`), `api/test/authz.test.ts` (matrix: role x permission x owner/non-owner, unknown permission denied, `anon` denied). Source of roles when needed: code-declared map plus `app_user.role` column (new migration), not JWT claims, until D3 is decided.

**T8. Client session contract for the Ky client (Plan 03).** Do not change Angular code. Specify in the Plan 03 interface and test against it: attach `Authorization` only to same-origin `/api/` and never `/api/v1/config`, `/health`, `/version`, `/releases`; single-flight refresh; one retry on 401; no refresh on 403/422/5xx/503; do not blindly replay mutations that returned a response other than 401; on refresh failure call `signOut('local')` and clear per-user cache (`data-cache.ts`); treat 503 as transient. Port unit tests from the behaviors in F11. Files (future): `web/src/**/http client`, `web/src/auth/*` replaced.

**T9. ADR: SDK-managed session vs BFF cookies.** Write `docs/adr/` entry (create directory only when D5 is answered). Compare: XSS exposure of `localStorage` tokens (F12), CSRF handling, serverless cost, Supabase SSR cookie flow, effect on Ky/TanStack Query. Recommendation to propose: keep SDK-managed for this product, require CSP + no inline script (Plan 01), revisit if a second product handles more sensitive data. No code.

## 4. Acceptance criteria

- A1. `npm test` passes; every route taking an id has an A-vs-B test returning 404 and leaving A unchanged (T2).
- A2. A token with the seed email but unverified email cannot claim `SEED_APP_USER_ID` (T4); verified token still can.
- A3. Supabase `/auth/v1/user` returning 500 or 429 yields 503 and the web client keeps the session (T3, F3).
- A4. Garbage HS256 tokens do not produce more than one upstream call per token hash per window (T3).
- A5. API refuses to start without auth on a non-loopback host unless explicitly overridden (T5).
- A6. `authorize()` denies by default; matrix test covers every declared permission (T7).
- A7. F7 has a written decision and either a passing isolation test or a documented accepted risk (T6).
- A8. ADR merged; Plan 03 references the T8 contract.

## 5. Risks

- T4 locks out the owner if the hosted project does not mark their email verified (OAuth GitHub users usually are; password signups with confirmations off are not). Mitigate by confirming D4 before deploy and keeping `SEED_OWNER_EMAIL` as a documented recovery path.
- T6 option A/B needs a data migration on live `game` rows; take a backup first (Plan 06 backup test).
- T3 negative cache is per instance on Vercel; limits the effect but is not global.
- T7 can become speculative; keep it to one role until a second consumer exists (YAGNI, analysis §13).
- Roles in JWT claims (analysis §6.5) go stale until refresh (up to `jwt_expiry` 3600s, `supabase/config.toml:166`); the plan avoids claims for roles for that reason.

## 6. Dependencies on other plans

- **Plan 01 (API errors):** shared edits to `server.ts` (lines 68-70, 178-181, 208-216). Order: Plan 01 Problem Details lands first or in the same PR so 401/403/404/503 use stable codes (`AUTH_REQUIRED`, `TOKEN_EXPIRED`, `FORBIDDEN`, `AUTH_UNAVAILABLE`). Plan 01 owns the owner-scope audit of queries; T2 here is the executable proof and should be shared, not duplicated. Plan 01 owns T5.
- **Plan 03 (React):** consumes T8 as the Ky/Query contract. Single retry owner must be the Ky layer for 401; Query must not retry 401/403. Per-user cache key must include `app_user.id` and be cleared on `SIGNED_OUT`.
- **Plan 04 (UI kit):** `PermissionGate` may only render hints from a server-provided permission list; no client-side security decision. Blocked until T7 exposes a permissions endpoint, which is optional and deferred.
- **Plan 05 (observability):** log `requestId`, `userId` (opaque), outcome code; never `Authorization`, tokens or email (analysis §5.3). Browser collector must authenticate via the same `authenticate()`; audit log of role changes arrives only if roles become editable.
- **Plan 06 (quality/ops):** hosts the security matrix CI job running T1/T2/T7 tests; decides canonical migration tree (F14); needs a `DATABASE_URL` test database in CI for T2.

## 7. Open decisions for the owner

- D1. Is the `game` table a shared catalog (any user may edit shared fields) or private per user? Drives T6.
- D2. Are there roles beyond "owner of own data" (analysis §16.3 item 3)? If no, T7 stays a one-role seam; if organizations or sharing are planned, scope them in a separate plan.
- D3. If roles arrive: code-declared with `app_user.role` in the database (recommended), JWT claims via `custom_access_token` hook, or runtime-editable? Revocation latency requirement?
- D4. In the hosted Supabase project: are email confirmations enabled, is public signup intended (`signup_disabled` message exists in the web client), and is the GitHub provider on? Is the project on JWT Signing Keys (asymmetric) or legacy HS256?
- D5. SDK-managed session or BFF cookies for this and future products (analysis §16.3 item 2)? Plan recommends SDK-managed for now.
- D6. Is the `<username>@gps.dev.br` alias login (`auth.service.ts:30,104`) a permanent feature? It affects email-based seed claiming and verification rules.
