# Reusable complete-project review request

Use the canonical project-review skill and evaluate the current project with experienced engineering judgment. Read every first-party text file completely, one file at a time, including implementation, callers, tests, schema evolution, configuration, scripts, and documentation. Record inspected line ranges and content hashes. Explicitly account for binaries, duplicated vendor material, generated data, ignored files, inaccessible files, and secrets. Do not describe structural parsing or sampled content as complete semantic reading.

Evaluate correctness, all SOLID principles with particular attention to Open/Closed, dependency direction, appropriate design patterns, security, operational resilience, performance, scalability, maintenance cost, and human readability. Prefer simple code that another developer can understand over speculative abstraction. Explain concrete future change scenarios and how existing behavior remains protected.

Evaluate the target of 1,000,000 simultaneous users and 1,000,000 requests per second. Distinguish workload assumptions from evidence and define the missing latency, traffic mix, payload, dataset, consistency, geography, duration, and cost requirements. Identify source-level obstacles and specify representative measurements needed to establish capacity. Do not infer a capacity guarantee from static review or passing functional tests.

Create the skill and its harness routing before launching reviewers if they do not exist. Delegate explicit file coverage to subagents, all using the same generic skill, mission, and workload target. Each reviewer must write a dated area report in `AI/project-review/yyyy-mm-dd/`, citing source paths, line numbers, confidence, severity, triggers, compatibility risks, and verification criteria. Preserve earlier runs.

The principal agent must read every completed report in full, independently verify each finding against source and contracts, resolve duplicates and disagreements, and record accepted, corrected, rejected, or unresolved dispositions. Produce a central summary with an honest coverage verdict, executed checks, strengths, limitations, and a prioritized unchecked improvement checklist containing minimal compatible changes, dependencies, regression protection, and measurable acceptance criteria. Leave application changes for a subsequent user-authorized implementation task.
